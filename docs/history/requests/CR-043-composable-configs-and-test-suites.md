# CR-043: composable configs, and test suites in place of presets

- **Requested by / date:** owner, 2026-11-04 ("PRESETs and recipes should be moved to a testing suite gaza being one of them. for specs and configs, there should be composable yamls."). Decisions, all as recommended: the suite lives in ponzi-core `suites/`; a case is a whole test location; composition is `extends:` with a deep merge; named presets go, and recipes are paths only.
- **Status:** implemented on the owner's instruction (2026-11-04), awaiting review; uncommitted

## Why

- **Named test cases were Python constants.** The Gaza release's recipe was hard-coded as `PRESETS["gaza_release_v4"]` in the library, and its fit spec sat among the general specs. Nothing said, in one place, what the Gaza test location is.
- **Configs repeated themselves.** The ten fit specs ran 60 to 98 lines each and differed in a few keys. The Gaza spec differed from `tide_c30_pdcompact` in 9 lines, and each candidate in 1 to 6.

## What changes

**Composition (`ponzi_spec.compose`):**
- `extends:` names a file, or a list of files merged in order, relative to the file that writes it.
- It can appear at the top of a document, or open any mapping inside one (`recipe: {extends: ../suites/gaza/recipe.yaml, code: 55}`).
- Mappings merge key by key at every depth. Lists, values and null replace what the bases had. The file's own keys win.
- A base is composed itself first. A cycle, a missing file, or a base that isn't a mapping is refused.
- `extends` is a reserved key. No config of PONZI has a field of that name.

**Composed loaders:** run configs (C4), fit specs, recipes, standards, panel specs, and coherence and onboarding configs.
- Each validates and hashes the composed document, so a composed file and its flat equal are the same config, with the same `config_hash`, recipe digest and spec.
- A run config's `name` is not inherited from a base. It is the file's own, or else its stem.
- `ponzi` now depends on `ponzi-spec` (pydantic and pyyaml only), so there is one implementation of the rule.

**Presets go:**
- `ponzi.products.PRESETS` is removed. `load_recipe`, `--recipe` (`ponzi detect`, `detect-path`, `tile`) and a standard's `recipe` take a file or fields.
- A preset name, or a `preset:` key, is refused with a message naming the file to build on instead.
- The worker's detect and tile stages take fields only.
- Content ids and recipe digests don't change, because they were always computed from the validated recipe.

**Test suites (`suites/`):** one folder per test location, each with a `README.md` that says what the case is and what's missing.
- `suites/gaza/recipe.yaml`: the former preset, field for field, with the same digest.
- `suites/gaza/fit_spec.yaml`: moved from `data/specs/tide_c30_gaza_f1p.yaml`, and composed on `data/specs/tide_c30_pdcompact.yaml`.
- `suites/gaza/area.yaml`: the AOI registry's columns (C13), plus burst ids and the source. The outline is the World Bank Official Boundaries' Admin 1 unit PSE001 "Gaza" (CC BY 4.0), rounded to 6 decimals, with the source file's sha256 (owner, 2026-11-04: "lets do world bank"). The bursts are the 12 of the OPERA burst database whose footprint meets it, on tracks 87 and 160 (ascending) and 94 (descending); each track covers the whole Strip. The event date is 2023-10-07.
- Not yet included: the registered model's run config and a Gaza standard. Both are on the HPC.

**Fit specs:** the candidates build on `tide_c30_pdcompact.yaml`, or on their family: `previous_aug` and `previous_cd` on `previous`, `previous_aug_s1` on `previous_aug`, and `sentinel_flag` on `sentinel`. Each file keeps its header comments.

`data/run_configs/exp_b5h5_base.yaml` is generated by `ponzi-paper campaign` and is left as it is. Composition is available to run configs from now on.

## Do results change?

No. Every rewritten fit spec resolves to exactly the document it was before, and to an equal `TideSpec`. The Gaza recipe has the former preset's digest. A composed run config hashes like its flat equal. Content ids are computed from validated configs, so they're unchanged.

Breaking for anyone who names a preset: `--recipe gaza_release_v4`, `preset:` in a recipe file, or `recipe: gaza_release_v4` in a standard. A standard on the HPC that names a preset has to give its fields, or `{extends: PATH}`.

## Tests

- ponzi-spec `test_compose.py`: the merge, relative paths, order, nested `extends`, a base used twice, and refusals (cycles, missing files, non-mappings, bad `extends`).
- ponzi `test_suites.py`: every case has a README and is listed; every suite file composes and every recipe loads; the Gaza recipe equals the former preset with the same digest; the area's shape; a composed run config hashes like the flat one, and an override deep-merges and changes the hash.
- The detection tests read the release's recipe from the suite, and the refusal of names and `preset:` is tested. The fit spec test reads the Gaza spec from the suite. The standard test refuses a preset name and a `preset:` key. The worker's plan test shows the recipe's id doesn't depend on how it's spelled, and refuses a name.
- Results: `pixi run test` (542 passed, 14 skipped), `test-models`, `test-pipeline` and `test-spec` pass, and ponzi-service passes 115.

## Version

- ponzi-spec: minor (`compose` is new), in the unreleased 0.4.0.
- ponzi: an interface removal (`PRESETS`, preset names) with no change to any store, contract or result. Under the version rules that is not MAJOR, but callers that name a preset break. Release it with a note.

**Renamed (owner, 2026-11-04):** `suites/` is now `testcases/`, and `test_suites.py` is `test_testcases.py` ("suites is ambiguous. use 'test' or something similar as it is just for testing"). The text above keeps the old name.
