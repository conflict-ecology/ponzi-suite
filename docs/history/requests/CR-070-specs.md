# CR-070: training, scoring, panel, detection, coherence and onboarding specs

- **Requested by / date:** owner, 2026-11-05 ("lets do training spec and scoring spec. Their respective folders in the .ponzi home dir should be plural versions of their names. ie training_specs scoring_specs", then the same pattern for the panel, detection, coherence and onboarding files, and the folders in both the suite and the home; "no need for backward compatability", then "full recompute. full rebuild.", then, on how versions are kept, "add 1 and 2 in CR070": a bump command and versions assigned at registration; then "remove the panel spec version. same with detection, coherence, onboarding specs. those should be hashes with the specs git tracked"; then "add new standard to CR070 sensor-scope as well. for those wheres, make sure the naming convention matches")
- **Status:** signed off (2026-11-05), implemented (2026-11-06)

## Why
Two of the files a model is made from have names that do not say what they are:

- **Fit spec**, in a folder called `forecasters/`, is how a model is trained (the kind of model, its hyperparameters, its inputs, the window, missing values, augmentation, seed). The folder name confuses it with the forecaster, which is the code.
- **Run config** is how a trained model is applied to a burst (the forecaster and its run-time parameters, the context, the scoring pyramid, the aggregation, the state machine). "Run" already means a run request, a staged run and a workflow run, and "config" names half a dozen other files.

The other files a person writes to say how something is made carry four more words (definition, recipe, config, config). One word, **spec**, for every such file, with the thing it makes in front, says what each is and how they relate: a training spec trains a model, a scoring spec applies it.

## What changes

**Names.** A spec is a file a person writes, validated by PONZI, that says how something is made; its content enters the identity of what it makes.

| Was | Becomes | Says how this is made |
| --- | --- | --- |
| fit spec | **training spec** | a trained model |
| run config | **scoring spec** | the runs of a model over a burst |
| panel definition (`panel.yaml`) | **panel spec** | a built panel |
| detection recipe | **detection spec** | the events and cells from p-values |
| coherence config | **coherence spec** | a burst's coherence store |
| onboarding config | **onboarding spec** | a store's sidecar and pixel sample |

Not specs, unchanged: the standard (a bundle naming specs and what was made from them), the model, the calibration and the built panel (made, not written), the workflow (generated by `standard-workflow`), the site file, the cluster profile, the server settings, an area.

**Folders.** The suite keeps the specs under git, and the PONZI home holds the working copies the tools read by default, under the same plural names:

| Suite (was) | Suite (becomes) | Home (new) |
| --- | --- | --- |
| `forecasters/<family>/<inputs>.yaml`, `candidates/` | `training_specs/<family>/<inputs>.yaml`, `candidates/` | `$PONZI_HOME/training_specs/` |
| `run_configs/<name>.yaml` | `scoring_specs/<name>.yaml` | `$PONZI_HOME/scoring_specs/` |
| `panels/<id>/panel.yaml` (with its geojson) | `panel_specs/<id>/panel.yaml` | `$PONZI_HOME/panel_specs/` |
| (inside each standard) | `detection_specs/<name>.yaml` | `$PONZI_HOME/detection_specs/` |
| (inside each standard) | `coherence_specs/<name>.yaml` | `$PONZI_HOME/coherence_specs/` |
| (inside each standard) | `onboarding_specs/<name>.yaml` | `$PONZI_HOME/onboarding_specs/` |
| `testcases/<case>/forecaster.yaml`, `recipe.yaml` | `testcases/<case>/training.yaml`, `detection.yaml` | |

Built panels stay in `$PONZI_HOME/panels/<id>/`. Detection, coherence and onboarding specs leave the standard: each is a file of its own, git tracked like the others, and a standard names them. `ponzi_spec.home.Layout` gains the six folders, made by `Layout.make`. A command that takes a spec by name looks in the home's folder first, then in the suite's (`$PONZI_SUITE`), and a path is always accepted.

**Code: one name pattern, one module per spec.** The old names are removed (no aliases). Every spec has a class `<Kind>Spec`, in a module `<kind>_spec.py`, read by `load_<kind>_spec` and written by `dump_<kind>_spec`, taken on the command line as `--<kind>-spec NAME|FILE`, and its parts are named `<Kind><Part>`, so a part never reads as a spec of its own:

| Spec | Was | Becomes |
| --- | --- | --- |
| training | `ponzi_models/training/fit_spec.py`: `TideSpec` | `ponzi_models/training/training_spec.py`: `TrainingSpec` |
| scoring | `ponzi/core/config.py`: `RunConfig`, `ContextConfig`, `ForecasterConfig`, `ScoringConfig`, `AggregateConfig`, `StateMachineConfig`, `load_run_config`, `dump_run_config`, `composed_run_config`; `--run-config` | `ponzi/core/scoring_spec.py`: `ScoringSpec`, `ScoringContext`, `ScoringForecaster`, `ScoringPyramid`, `ScoringAggregate`, `ScoringStateMachine`, `load_scoring_spec`, `dump_scoring_spec`, `composed_scoring_spec`; `--scoring-spec` |
| panel | `ponzi_models/panels/spec.py`: `PanelSpec`, `CellsSpec`, `ClassifierSpec`, `SelectionSpec`, `SplitSpec`, `WindowSpec`, `DrawSpec`, `load_panel_spec` | `ponzi_models/panels/panel_spec.py`: `PanelSpec`, `PanelCells`, `PanelClassifier`, `PanelSelection`, `PanelSplit`, `PanelWindow`, `PanelDraw`, `load_panel_spec`, `dump_panel_spec` |
| detection | `ponzi/products/recipe.py`: `DetectionRecipe`, `load_recipe`, `recipe_fields` (with the detection functions) | `ponzi/products/detection_spec.py`: `DetectionSpec`, `load_detection_spec`, `detection_spec_fields`; the functions stay in `ponzi/products/detection.py` |
| coherence | `ponzi_pipeline/config.py`: `CoherenceConfig`, `Looks`, `Window`, `Grid`, `Dem`, `load_coherence_config` | `ponzi_pipeline/coherence_spec.py`: `CoherenceSpec`, `CoherenceLooks`, `CoherenceWindow`, `CoherenceGrid`, `CoherenceDem`, `load_coherence_spec` |
| onboarding | `ponzi_pipeline/onboard/config.py`: `OnboardingConfig`, `load_onboarding_config` | `ponzi_pipeline/onboard/onboarding_spec.py`: `OnboardingSpec`, `load_onboarding_spec` |

The keys inside a spec's file do not change (`context`, `forecaster`, `scoring`, `aggregate`, `state_machine`, ...): they are its content. `config_hash` becomes `ScoringSpec.spec_hash` (and every spec class gets `spec_hash`), the registry entry's `run_config.yaml` becomes `scoring_spec.yaml` (and a model's training spec is kept beside it as `training_spec.yaml`), and the worker's stage parameter classes keep their own names (`RunParams`, `DetectParams`, ...), holding the specs under the keys below. `ponzi_spec.naming` names the kinds `training spec`, `scoring spec`, `panel spec`, `detection spec`, `coherence spec`, `onboarding spec` and `standard`, and a test holds every spec module, class, loader and flag to the pattern.

**Stored fields, renamed.** There is no backward compatibility: the old names are not read.

| Where | Was | Becomes |
| --- | --- | --- |
| model card (`model.json`) | `run_config_name`, `run_config_hash` | `scoring_spec_name`, `scoring_spec_hash` |
| registry entry | `run_config.yaml` | `scoring_spec.yaml` |
| calibration (`calibration.npz` meta) | `run_config_hash` | `scoring_spec_hash` |
| standard (bundle) | `run_config_hash`, `recipe` | `scoring_spec_hash`, `detection` |
| training spec | `fit_id` | `training_id` |

A file with an old name is refused with a message naming the new one. The suite's specs and standards are rewritten here; registries are rebuilt, not rewritten (below).

**Identity: a full rebuild.** The hashed parameters take the new names too, and every stage's identity version is raised to `2`, so every content id changes and everything is made again from the SLCs:

| Stage parameters | Was | Becomes |
| --- | --- | --- |
| `run` | `config`, `config_name` | `scoring_spec`, `scoring_spec_name` |
| `detect`, `tile` | `recipe` | `detection` |
| `discover`, `dem`, `coherence`, `assemble` | `coherence` | `coherence` (the word already fits; the version raise makes their ids new) |
| `onboard` | the onboarding fields | unchanged fields, new version |

Every stage's `version` becomes `"2"`, ingest stages included. The worker's cache, a home's `outputs/`, the server's jobs and Items, and any built panel are thrown away and made again; nothing is migrated. The registry is rebuilt: each model in use is registered again from its exported artifact (no retraining) with its scoring spec, and each calibration is made again on the new runs (`null-runs`, `calibrate`, `register-calibration`), since a calibration is made for the runs of one scoring spec. A scoring spec's hash is over its content, whose keys do not change, so a model's `scoring_spec_hash` is the value its `run_config_hash` was.

**Versions: only the standard has one.** Every spec is known by its name and its content hash, has no version, and is git tracked in ponzi-suite; a different spec is a new name. The standard, the bundle people and the server cite, is the one thing with `MAJOR.MINOR.PATCH`, written by a command and held to its content by a hash.

- **A content hash for every spec, over its resolved settings.** Each spec is read by its class in the code (`TrainingSpec`, `ScoringSpec`, `PanelSpec`, `DetectionSpec`, `CoherenceSpec`, `OnboardingSpec`), which fills every setting the file leaves out with the code's default; the hash is over that resolved document's canonical JSON (without its `name`), as the scoring spec's `config_hash` is today. A changed default in the code is then a changed hash, so a spec cannot silently mean something else under new code. A panel spec's hash also covers its geojson files (by name and bytes); a standard bundle's covers its fields and the hashes of the specs it names. The scoring spec keeps its present hash function, so a model's `scoring_spec_hash` stays the value its `run_config_hash` was; the others use the same function (`ponzi_spec.identity.digest_bytes`).
- **The panel spec loses its version.** `version` leaves `panel.yaml`; a panel is cited by its id (`majortom-global`) and pinned by its hash. A model id is `<training spec>--<panel spec>` (`tide-weather--majortom-global`), no longer with the panel's version; a built panel is `$PONZI_HOME/panels/<id>/`, its record holding the spec's hash. A changed panel (other cells, another draw) is a new panel spec under a new name (`ponzi_spec.naming` gains the words for it). `PANEL_KEY` and `id@version` for panels go.
- **A standard names its specs.** The bundle's `coherence`, `onboarding` and `detection` are the names of their specs (in place of their fields), and `panel` is the panel spec's name. When a standard is checked or registered, each name is resolved (the home's folder, then the suite's) and its hash recorded.
- **Where a spec is used, its name, hash and suite commit are recorded**, as one `specs:` block: on a model card (its training, scoring and panel specs), on a built panel's record (its panel spec), on a calibration (its scoring and panel specs), on a standard's registry record and in the server's standard file that `standard-workflow` writes (every spec it names, and the bundle). `suite_commit` is the ponzi-suite commit the file was read from (`git rev-parse HEAD` and a clean file), or `null` when it is not in a commit, which is said on the record.
- **A spec is frozen once used.** A name stands for one hash: registering a model, building a panel or registering a standard with a spec of a known name and another hash is refused, saying to give the changed spec a new name. The registry keeps the hash each name was first used with (`specs.json`).
- **The standard's name: `<sensor>-<scope>`.** A standard's `id` is its sensor and its scope, both words listed on the Naming page and checked by `ponzi_spec.naming`: sensors `s1` (later `nisar`), scopes `general` and a test case's name (`s1-gaza`). The sensor is a deliberate exception to "no sensor in a name": a standard runs one sensor's data, and the model card's `sensor` must match it. `check-standard`, `register-standard` and the suite's tests refuse any other form.
- **`new-standard`, a standard generated from the registry.** `ponzi-models new-standard --model MODEL_ID --detection-spec NAME --coherence-spec NAME --onboarding-spec NAME [--scope general] [--calibrations ID,...] [--description TEXT]` writes a standard's first version without anything copied by hand:
    - from the registry: the model's reference (`registry:<id>@sha256:<digest>`), its scoring spec's name and hash, its panel spec's name and hash, and its calibrations (all of them, or those named);
    - its `id`, `<sensor>-<scope>`, from the model card's sensor and `--scope`, refused when a standard of that id is registered already (a new version of one is made by editing it and `bump-standard`);
    - each named detection, coherence and onboarding spec, resolved (the home, then the suite) and hashed;
    - `requires`: the installed versions of the distributions its stages' code is, as lower bounds (`ponzi>=0.3.0`);
    - `status: draft` and version `1.0.0`, written to `$PONZI_HOME/standards/<id>-1.0.0.yaml` (or `--out`), then checked with `check-standard`. It is published by setting `status: published` and `register-standard`.
- **1. A bump command for the standard.** `ponzi-models bump-standard FILE` compares the edited bundle with the latest version recorded in the registry (else with the highest earlier file beside it), chooses the bump from what changed, and writes the next version:
    - a change to `RUN_IDENTITY` (sensor, workflow, the coherence and onboarding specs, the panel spec, the model, the scoring spec) is a major, to `MINOR_FIELDS` (the calibrations, the detection spec) a minor, to the description or `requires` alone a patch (the rules `check_versions` holds today, CR-055), a spec counting as changed when its name or its hash does;
    - the new standard is written beside the old one as `<id>-<version>.yaml` with its `version` filled in;
    - it prints each changed field and the bump it implies. `--version X.Y.Z` asks for a larger bump, never a smaller one. Nothing changed: nothing is written.
- **2. The standard's version assigned at registration.** The registry gains `standards/<id>@<version>/` (the bundle and its `specs:` record), written once. `ponzi-models register-standard FILE`:
    - with no `version` in the file, assigns the next one from the latest registered version and the rule above, and writes it into the file;
    - with a `version`, checks it: it must be later than the latest registered, and at least the bump the change needs;
    - refuses an `id@version` already registered with another hash ("raise the version"), and accepts the same hash again as a no-op;
    - refuses `status: published` from a bundle, or a spec it names, not in a ponzi-suite commit, unless `--allow-uncommitted` is given, which the record then says.
  `check-standard` checks against the registry's latest version when there is one. A draft standard is registered like any other: its version is citable from then on.

## Do results change?
The numbers do not: the same code on the same inputs under new names. Every content id changes, and every output, calibration and built panel is made again. Each calibration made again is checked against the one it replaces (the same thresholds within floating-point noise, the same seed).

## Tests
- The outputs are the same before and after: the demo and the rehearsal are run on both sides, and every asset's bytes (or a store's arrays) are equal under the new content ids; only the ids and the renamed metadata fields differ.
- Every stage's content id changes (`test_identity.py`), and no cache entry made before is found.
- The registry reads an entry with `scoring_spec.yaml` and `scoring_spec_hash`, and refuses one with the old names, saying what to run; the same for a calibration and a standard.
- A model registered again from its artifact has the same artifact digest and a `scoring_spec_hash` equal to its old `run_config_hash`.
- A scoring spec's hash is the same as the run config's it replaces (the reference `rolling-ols-pyramid`).
- `Layout.make` makes the new folders; a spec found by name in the home is preferred to the suite's.
- `ponzi_spec.naming` and `test_suite_names.py` hold the suite's renamed folders to the rules.
- A spec's hash changes with any edit that changes a resolved setting, and with a changed code default for a setting the file leaves out; not with key order, comments, or writing out a default explicitly. A panel spec's also with any of its files.
- A panel spec with a `version` is refused; a model id is `<training spec>--<panel spec>`; a built panel's record holds its spec's hash.
- A standard naming a detection, coherence or onboarding spec resolves it and records its hash; one giving the spec's fields inline is refused.
- A spec of a known name with another hash is refused wherever it is used (model, panel, standard).
- `bump-standard` gives a major for a new model, scoring, panel, coherence or onboarding spec, a minor for new calibrations or a new detection spec, a patch for a new description, refuses `--version` smaller than that, and writes nothing when nothing changed.
- `register-standard` assigns the next version when none is given, refuses a reused `id@version` with another hash, accepts the same content again, and refuses an uncommitted published standard (or spec) without `--allow-uncommitted`.
- A model card, a built panel, a calibration, a standard's record and the server's standard file carry the `specs:` block with the right names, hashes and commit.
- A standard id not of the form `<sensor>-<scope>` with listed words, or whose sensor is not its model's, is refused.
- `new-standard` from a registered model writes a draft that `check-standard` passes, with the model's reference, scoring and panel spec hashes and calibrations from the registry, and refuses an id already registered.
- Every spec module, class, loader and command-line flag follows `<kind>_spec.py`, `<Kind>Spec`, `load_<kind>_spec`, `--<kind>-spec`, and no spec part is named `...Spec` or `...Config`.

## Version
`ponzi-spec`, `ponzi`, `ponzi-pipeline` and `ponzi-models` major (names removed; below 1.0 a new `0.y`), and ponzi-service the same. Every standard takes a new major version (its runs are made again under new content ids, its calibrations are new, and its specs are now named files): `s1-general` becomes `2.0.0`, still a draft. The panel `majortom-global@0.4.0` becomes the panel spec `majortom-global` (its content unchanged), and the model `tide-weather--majortom-global-0.4.0` is registered again as `tide-weather--majortom-global`.

## Order of work
1. ponzi-core: the before-and-after output test first (the outputs recorded under the current code), then `ponzi_spec` (home layout, naming, spec hashes), the libraries' classes, the panel spec without a version, the registry (the `specs:` block, `specs.json`, the standard records), the standards naming their specs and named `<sensor>-<scope>`, and the `new-standard`, `bump-standard` and `register-standard` commands.
2. ponzi-service: the worker's stages take the new class names and parameter keys and version `2`; the server reads standards under the new names and lists each one's hash and suite commit (`GET /v1/standards`).
3. ponzi-suite: `git mv` the folders, rename the test case files, move each standard's detection, coherence and onboarding fields into named spec files, drop the panel spec's `version`, rewrite `standards/` (`s1-general-2.0.0.yaml` by `bump-standard`), update the docs (terminology, naming, models, standard versions, the method pages) and `llms.txt`.
4. The owner clears each cache, outputs folder and server database, registers the models in use again, makes their calibrations again (on the cluster), registers each standard (`register-standard`), and copies the new standards to each server; watched areas are made again.
5. ponzi-visual: no change (it sees no specs).
