# A new model

From a fit spec to a model watched areas run, with the command `ponzi-models` (`ponzi-models --help` lists the stages).

The steps below are written for a trained forecaster, such as TiDE, today's default. Any forecaster can take its place: a new kind is added as a module of `ponzi.core.forecast` with one `register(name, cls, params)` call, and then follows the same steps (one that fits itself as it runs, like `rolling_ols`, skips training and export). The scoring, the calibration, the detection and the service do not change with the forecaster.

1. **Change request**, with the evidence the model is meant to improve on.
2. **Fit spec** in ponzi-suite `forecasters/<family>/` (a variant in `candidates/`, built on its base with `extends:`), named by the [naming convention](../reference/naming.md): window (context, horizon, baselines, quantile levels), covariate channels, sizes, optimiser, stopping, treatment of missing values, augmentation. Unknown keys are refused.
3. **Panel**: a set of pixels of many bursts, defined by mask layers on full coherence stores. Its definition is kept in ponzi-suite `panels/<id>/` and checked with `ponzi-models panel-check`; `ponzi-models panel-build` builds it into `{home}/panels/<id>@<version>`. Training, calibration and production read the panel through the same opener, so a training window is byte for byte the window inference builds.
4. **Prepare, train, export** (`ponzi-models prepare`, `train`, `export`): the prepared files are identified by a digest of what they depend on; training keeps the epoch with the lowest validation loss; export writes the artifact (for TiDE, TorchScript and its `meta.json`).
5. **Register** (`ponzi-models register-model`) the model, its id `<forecaster>--<panel>-<version>` (the name `export` gives the artifact) in the registry (`{home}/registry` by default) with its model card: the artifact by its digest and the run config it runs with. Configs refer to the model as `registry:<model id>@sha256:<digest>` (`ModelEntry.ref`), never by path; the run resolves it through the registry and checks the digest.
6. **Null and calibrate** (`ponzi-models null-runs`, `null-rows`, `calibrate`, `register-calibration`): run the registered model over the panel's test bursts; build the calibrations (plain and ceiling) from those runs. For staged runs (CR-021), `null-runs --staged` and `calibrate-staged` build the staged (format 3) pair instead. A calibration is bound to one run config hash and one major version of `ponzi`.
7. **Benchmark** against the current standard. A model joins a standard only after the benchmark. There is no benchmark command yet.
8. **Standard**: a yaml file in ponzi-suite `standards/<id>-<version>.yaml`, checked with `ponzi-models check-standard`. A new standard version names its panel, the model, its run config, its calibrations, the detection recipe, the workflow and the library versions it `requires`. It starts as a draft (`status: draft`) and is published once its model and calibrations are registered. `check-standard` holds it against the registry, the installed versions, the built panel (no training cell may be a test cell) and the version before it. `ponzi-models standard-workflow` turns it into the file the server runs, which goes into the server's standards folder (`{home}/standards` by default).
